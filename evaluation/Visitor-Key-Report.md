# Visitor-owned API keys — version 0.8.0

Visitors can select API key in the header or Use AI with my key on the welcome screen, enter their own OpenAI key, and use AI without downloading the app. The credential is held in a per-tab closure and sent in the Authorization header to the configured backend per AI request. The password input is cleared on use and close. No key is added to chat context, model input, saved chats, exports, browser storage, URLs, GitHub source or application logs. Refresh, page hide and Clear my key remove the application reference; in-flight requests are cancelled on key changes. This is not a claim that credentials cannot be inspected by the page, browser extensions or hosting infrastructure. The UI explains the backend destination and asks visitors to trust the app and hosting.

The public Worker requires a visitor key on each request and ignores the owner's stored API key. A malformed/missing key is rejected before model execution. A provider-rejected key is not retried with another credential. Browser keys override a local private server key only within that tab; clearing the override restores that local configuration. Public Node hosting also requires a visitor key. Shared availability limits still apply.

122 app tests and three hosted API tests passed. Tests cover isolated key holders, safe errors, distinct visitor credentials, absence of owner fallback, local-key override, and Authorization preflight handling, alongside the existing agent/retrieval/history suite. Browser checks with a synthetic key confirm format errors, loading, clearing, refresh reset, retained chat history and provider-401 reset to practice. A real credential was used only through a scripted request to verify the public backend; it was not printed or written into the verification report.

Live hosted checks: missing key → 401, invalid key → 401 with safe error, valid visitor key → 200 with Resume specialist and review_resume completion; CORS preflight → 204 permitting Authorization. The previous backend alias also reports visitor-key mode. Results are in visitor-key-hosted-checks.json and visitor-key-browser-checks.json. These checks validate credential routing and UI behavior, not general factual quality.

The GitHub Pages interface becomes available after the prepared source commit is pushed and its publishing workflow completes. Keys are never included in the distributable source.
